# Brew & Bean — Café POS

A working café point of sale built with React, Tailwind CSS, Express, and PostgreSQL. Everything lives directly inside this existing `Cafe-POS` folder.

## Start the project

Requirements: Node.js 22.12 or newer (tested with Node.js 24), npm, and a modern browser. The included development runtime runs a **real PostgreSQL 18 server**. Docker and an existing PostgreSQL installation are optional.

Open a terminal in the project folder and run:

```sh
npm install
npm run setup
```

`setup` creates `.env` with a random authentication secret and preserves an existing `.env`.

In terminal 1, start the local database and leave it running:

```sh
npm run db:local
```

Wait for **Local PostgreSQL ready**. In terminal 2:

```sh
npm run db:init
npm run dev
```

Open **http://127.0.0.1:5173** if the browser does not open automatically. The API runs at **http://127.0.0.1:4000/api/health**.

`npm run dev` opens the website automatically when the frontend is ready. Keep the database terminal running first. On Windows, Chrome is detected in its standard installation locations. To disable automatic opening for a terminal session, run `BROWSER=none npm run dev` on macOS/Linux or `$env:BROWSER='none'` in PowerShell.

Use `127.0.0.1`, as configured in `.env`, rather than mixing it with `localhost`. The frontend proxies `/api` and `/uploads` to the backend, keeping authentication on the same origin. Do not reuse `.local-db/` across operating systems; back it up and create a fresh local database if it was initialized on a different platform.

On a new database, run `npm run db:init` once after starting PostgreSQL. After that, you only need `npm run db:local` and `npm run dev` in separate terminals. Keep both running. Stop them with **Ctrl+C**; stop the app before the database. Database contents persist in `.local-db/`. Do not delete that folder to restart the app.

To start the frontend or backend separately from the project root:

```sh
npm run dev -w backend
npm run dev -w frontend
```

The frontend refreshes when source files change. Restart the backend after changing backend code or `.env`.

| Cashier       | `cashier@cafepos.local` | `Cashier123!` |

Passwords in `database/seed.sql` are bcrypt hashes with cost 12. Use these accounts for local demonstrations. Replace demo credentials before a public deployment. A password reset helper is included:

```powershell
npm run user:password -- admin@cafepos.local
```

The helper prompts for the new password with input hidden. It does not put the password in shell history or process arguments.

Admins can use POS, Orders, Products, Sales Report, and Settings. Cashiers can use POS and Order History. The API enforces admin restrictions independently of the sidebar.

## Use your own PostgreSQL installation

Skip `db:local` when using an existing server. Create a database using pgAdmin, or run these commands with your PostgreSQL administrator account:

```sql
CREATE ROLE cafepos LOGIN PASSWORD 'choose-a-strong-password';
CREATE DATABASE cafepos OWNER cafepos ENCODING 'UTF8' TEMPLATE template0;
```

Update `.env`:

```dotenv
DATABASE_URL=postgresql://cafepos:YOUR_URL_ENCODED_PASSWORD@127.0.0.1:5432/cafepos
```

Use percent encoding for special characters in URL passwords. Run `npm run db:init`, which executes `database/schema.sql` and `database/seed.sql` against `DATABASE_URL`.

Alternatively, apply the files manually from the project root:

```powershell
psql -h 127.0.0.1 -p 5432 -U cafepos -d cafepos -f database/schema.sql
psql -h 127.0.0.1 -p 5432 -U cafepos -d cafepos -f database/seed.sql
```

For the included local runtime, use port `54329`. Its credentials are the `LOCAL_PG_*` values in `.env`. Existing accounts, settings, and named demo products are preserved when seeding again. Schema creation is intended for initial setup; use versioned migrations for later schema changes.

## Environment variables

| Variable            | Purpose                                                                     |
| ------------------- | --------------------------------------------------------------------------- |
| `DATABASE_URL`      | PostgreSQL connection string used by the API and schema setup               |
| `JWT_SECRET`        | Random signing secret, at least 32 characters; generated by `npm run setup` |
| `PORT`              | API port; defaults to `4000`                                                |
| `HOST`              | API bind address; defaults to `127.0.0.1`                                   |
| `APP_ORIGIN`        | Exact browser origin permitted to send state-changing requests              |
| `NODE_ENV`          | `development` locally; `production` enables Secure authentication cookies   |
| `BUSINESS_TIMEZONE` | Reporting timezone, initially `Asia/Phnom_Penh`                             |
| `LOCAL_PG_PORT`     | Local PostgreSQL port, initially `54329`                                    |
| `LOCAL_PG_USER`     | Local PostgreSQL administrator name                                         |
| `LOCAL_PG_PASSWORD` | Local PostgreSQL password set when the cluster is first initialized         |

The included development database is restricted to the loopback interface. Changing its password variable after initialization does not change an existing PostgreSQL role password; update the database role and connection URL together.

## Everyday workflow

### Products and images

Open **Products → Add Product**. Enter the name, price, category, and availability, choose an optional photo, then save. Use the pencil button to change the product name, price, photo, category, or availability. Use the trash button to remove a product after confirming.

Images accept JPG/JPEG, PNG, and WEBP, up to **5 MB**, with a 25-megapixel decoded-image limit. The backend validates the MIME type and actual image data, applies orientation, resizes to fit within 1200 × 1200, and saves a freshly encoded WEBP with a random filename in `backend/uploads/`. PostgreSQL stores only the `/uploads/...` path. Image metadata is stripped through re-encoding.

`backend/utils/storage.js` is the storage adapter. Replace `storeImage()` to support Cloudinary later. Serve returned URLs from your approved media domain and update the image CSP in `backend/server.js` if using an external image service.

Sample photos are local files under `frontend/public/images/`; attribution URLs are in `SOURCES.txt`. They are illustrative photos and should be replaced with the café's own product photos. The SVG fallback is used when a photo is unavailable.

Product edits refresh the menu immediately in the current app and within 15 seconds in other open POS screens. Existing carts adopt current prices and remove unavailable products. Checkout checks server prices and tax again. If they changed, review the updated total and reconfirm.

Deleted products are archived so previous receipts retain their items. Old uploaded files are deliberately preserved because existing receipts may reference them. A future cleanup job should remove only files with no current-product, settings, or receipt references.

### Checkout

1. Click menu cards to add products. Use plus, minus, remove, or **Clear All** to change the cart.
2. Enter an optional fixed-amount discount. Tax applies to the discounted subtotal.
3. Choose Cash, KHQR, or Card, then **Proceed to Payment**.
4. For cash, enter cash received. The system calculates change and blocks insufficient cash.
5. For KHQR, scan the café's uploaded image and check the café's bank app. Click **Payment Received** only after verifying the full payment.
6. For card, use your external terminal and confirm only after it approves the charge.
7. The server saves the order, item price snapshots, and payment in a single database transaction, then displays a receipt.

KHQR and card are manual confirmations. This version does not call ABA, generate amount-specific bank QR codes, read payment notifications, or process card details. Until the owner uploads a KHQR image, KHQR checkout is disabled.

Click **Print Receipt** to open browser printing. The print stylesheet formats only the receipt for an 80 mm roll; choose your printer and paper in the browser dialog, and disable browser headers/footers. **New Order** closes the receipt and returns you to the workspace.

The active cart stays intact when navigating between pages. Refreshing the browser, closing the tab, or logging out clears an unsaved cart. Version 1 requires an active API/database connection and does not support offline checkout.

Totals use integer cents on both client and server, with tax rounded once after discount. Server prices are authoritative. Each checkout has an idempotency UUID; simultaneous retries with that UUID return the same saved order. Order numbers contain a date and random suffix and are constrained to be unique in PostgreSQL.

### Orders and reports

Order History supports date, order-number, and payment-method filters, with 25 orders per page. Open an order to inspect or reprint its receipt. Cashiers can view the café's order history.

Sales Report reads PostgreSQL for today's revenue and order count, this month's revenue, average order value across all saved orders, best sellers, a seven-day chart, recent orders, and payment-method totals. There are no fabricated sales totals. Reports separate currencies instead of adding unlike currencies together. Daily boundaries use `BUSINESS_TIMEZONE`; displayed receipt/order timestamps use the browser's local timezone.

### Settings

Open **Settings → Menu & prices** to manage products directly from Settings. Click **Edit price & photo** beside a product, enter its new price, click **Replace photo** to choose a new picture, and select **Save Changes**. The preview shows the replacement before saving, and the POS refreshes after saving. Product name, category, and availability can be edited in the same dialog; **Add Product** creates a new menu item.

Use **Settings → Café details & images** for the café logo and KHQR image. Click **Replace logo** or **Replace KHQR image**, choose a file, and click **Save Settings**. Switching between these settings sections preserves unsaved café details.

The owner can change café name, address, phone, logo, currency, tax percentage, and KHQR image. Supported currencies are USD, KHR, EUR, GBP, and THB, displayed with two decimal places. Changing currency changes the denomination for new sales; it does not perform currency conversion or change the numeric menu prices.

Settings update the POS and all new receipts. Saved receipts retain a snapshot of the café details, currency, prices, and tax from the sale.

## Database and project structure

```text
Cafe-POS/
  frontend/
    src/components/     Shared controls, image fallback, dialogs, receipt
    src/context/        Authentication and automatically refreshed café data
    src/pages/          Login, POS, Products, Orders, Reports, Settings
    src/services/       API client and money/date formatting
    public/images/      Locally served sample menu photos and fallback
    src/App.jsx         Navigation and application shell
    src/main.jsx        React entry and error boundary
    src/styles.css      Tailwind import, responsive styling, receipt printing
  backend/
    config/             Environment and PostgreSQL pool
    middleware/         Authentication and role checks
    routes/             REST endpoints and transaction handlers
    utils/              Validation, errors, replaceable image storage adapter
    uploads/            Uploaded image files (not committed)
    server.js           Express app and production static serving
  database/
    schema.sql          Tables, relationships, constraints, indexes
    seed.sql            Demo users, categories, products, café settings
  scripts/              Environment setup, database lifecycle, image download
  tests/                API integration and Chrome browser tests
  .env.example          Configuration template
  package.json          Workspace commands
  package-lock.json     Reproducible dependency versions
```

Tables: `users`, `categories`, `products`, `settings`, `orders`, `order_items`, and `payments`. Orders reference their cashier; line items reference the order and product; each payment belongs to one order. Line items and receipt settings are snapshots to preserve historical receipts. SQL parameters are bound rather than interpolating user input.

## API

Authentication uses a 12-hour JWT in an HttpOnly, SameSite=Strict cookie. It is Secure over HTTPS in production. Tokens are never stored in localStorage. Logout removes the browser cookie. Login attempts are rate-limited, state-changing browser requests check their origin, and Helmet sets security headers.

| Method | Route                  | Access                                                      |
| ------ | ---------------------- | ----------------------------------------------------------- |
| GET    | `/api/health`          | Public database health                                      |
| POST   | `/api/auth/login`      | Public, rate-limited                                        |
| GET    | `/api/auth/me`         | Current user or null when no cookie                         |
| POST   | `/api/auth/logout`     | Clears cookie                                               |
| GET    | `/api/categories`      | Signed in                                                   |
| GET    | `/api/products`        | Signed in; cashier sees available products                  |
| POST   | `/api/products`        | Admin, multipart fields + optional `image`                  |
| PUT    | `/api/products/:id`    | Admin, multipart fields + optional `image`                  |
| DELETE | `/api/products/:id`    | Admin; archives product                                     |
| GET    | `/api/orders`          | Signed in; `date`, `number`, `method`, `page` query filters |
| GET    | `/api/orders/:id`      | Signed in                                                   |
| POST   | `/api/orders`          | Signed in; validated checkout transaction                   |
| GET    | `/api/reports/summary` | Admin                                                       |
| GET    | `/api/settings`        | Signed in                                                   |
| PUT    | `/api/settings`        | Admin, multipart fields + optional `logo` and `khqr`        |

Errors return `{ "error": "Human-readable message" }` with an appropriate HTTP status. No database credentials or stack traces are sent to the browser.

## Test and build

Start the database and `npm run dev` first. Run tests one suite at a time because they exercise the same development database:

```powershell
npm test
npm run test:e2e
npm run build
npm run test:build
```

API integration tests verify authentication, authorization, validation, image handling, product changes, exact financial calculations, all three payment methods, idempotency, order history, reporting, and settings. They restore the settings they modify and remove their test orders and test product.

Browser tests use installed **Google Chrome** in headless mode. For Edge on Windows:

```powershell
$env:PLAYWRIGHT_CHANNEL='msedge'
npm run test:e2e
```

The browser suite runs the requested **Test Latte → $3 × 2 → $10 cash → $4 change → receipt → history → report → edit to $4 with a new photo** workflow, plus cashier and settings/payment scenarios. Browser test sales remain visible as demonstration records. The most recent Test Latte remains at $4.00. Run the suite only against a development database; it creates real test sales, changes settings temporarily, and replaces an existing product named Test Latte.

The HTML browser report is `playwright-report/index.html`; visual evidence is written under `test-results/evidence/`. Browser print invocation and print layout can be tested, but a physical receipt printer is not required for the suite.

`npm run test:build` launches temporary Express servers on ports 4001 and 4002. It verifies the compiled frontend in Chrome, then checks the friendly error response when PostgreSQL is unavailable. The temporary servers stop when the check finishes. The normal app and database remain running. See [VALIDATION.md](VALIDATION.md) for the completed verification record.

Build output is `frontend/dist/`. With the frontend development server stopped, the backend serves the built app directly:

```powershell
npm run build
npm start
```

Set `APP_ORIGIN=http://127.0.0.1:4000` for this local built-app mode before starting, and open http://127.0.0.1:4000. Keep `NODE_ENV=development` for plain HTTP local testing.

## Deploy later

1. Provision a persistent PostgreSQL database and apply the schema. Create your own user accounts or replace the demo passwords. Use a database role limited to the application's needs; the included local runtime's role is a development administrator.
2. Configure `DATABASE_URL`, a new random `JWT_SECRET`, `NODE_ENV=production`, `APP_ORIGIN=https://your-cafe-domain`, and the business timezone. Set `HOST=0.0.0.0` if your hosting platform requires it.
3. Run `npm ci` and `npm run build` during deployment, then run `npm start` under a service/process manager. Use the backend's static serving to keep the app and API on one HTTPS origin.
4. Put HTTPS in front of Express. Production authentication cookies require HTTPS. If using a reverse proxy, configure Express `trust proxy` to your specific proxy topology before relying on per-client rate limiting; do not blindly trust arbitrary forwarded headers.
5. Mount `backend/uploads/` on persistent storage or replace the storage adapter with Cloudinary. Back up uploaded files together with PostgreSQL. Do not deploy `.local-db/`, `.env`, or test artifacts as public files.
6. Establish database backups, restore checks, monitoring, and an account/session management policy. JWTs expire after 12 hours; logout clears the local cookie. To invalidate all existing tokens, rotate `JWT_SECRET` and restart the backend.

The included embedded PostgreSQL package is for local development. A managed PostgreSQL service or standard PostgreSQL installation is recommended for an operating café.

## Troubleshooting

- **Database connection failed:** start `npm run db:local`, wait for the ready message, and check `DATABASE_URL`. For an external server, verify its port, username, password, and database name.
- **Port already in use:** a previous app/database may still be running. Stop that instance first. If changing the API port, also change the proxy target in `frontend/vite.config.js`.
- **Untrusted origin:** open the exact URL in `APP_ORIGIN`, then restart the backend after modifying `.env`.
- **Incorrect login:** use the demo credentials above, or reset the account using the password helper. Seeding again preserves existing passwords.
- **Upload failed:** select a valid JPG, PNG, or WEBP of 5 MB or less. Check write access to `backend/uploads/`.
- **Product or tax changed during checkout:** review the updated cart and confirm again. The server prevents saving a stale price.
- **KHQR button disabled:** upload the café's real payment image under Settings first. A sample menu photo is not a payment QR.
- **Order failed to save:** keep the payment dialog open and retry after connectivity returns. Check Order History if the response was interrupted after the payment was saved.
- **Dependency install blocked:** npm needs access to the package registry to download dependencies and PostgreSQL binaries. Allow the install through your development environment's network approval flow.

Version 1 does not include inventory tracking, refunds, voids, split payments, shifts, a user-management screen, automated bank verification, or fiscal-printer integration.
